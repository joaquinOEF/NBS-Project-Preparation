## 1. Executive summary (top risks)

_Flood-focused top five for city-facing decisions (full register §3–§4; detail in [flood audit](flood-risk-scoring-methodology-audit.md))._

| # | Risk | Impact | Gate / mitigation |
|---|------|--------|---------------------|
| 1 | **May 2024 depth in score (`floodEvidence`, EMSN194 15%)** — same disaster family as SkySat validation label | Inflates F1; map is **event-calibrated**, not a portable flood model | Do not claim reusable model; run **evidence-off** F1 ([flood audit §7](flood-risk-scoring-methodology-audit.md#7-flood-validation-critique-f1--70)); drop or replace term for other events |
| 2 | **“Flood risk” ≠ IPCC risk** — `flood_score` is hazard/susceptibility (no E×V in formula) | Overstates alignment with municipal risk studies | Say **flood hazard / screening** in external materials ([flood audit §2.6](flood-risk-scoring-methodology-audit.md#26-terminology-flood-hazard-vs-ipcc-flood-risk)) |
| 3 | **Custom flood formula risk** — annual FRI + AOI-dependent normalization + tuned weights | Weak event transfer; hard to justify as city-grade model | Prefer externally validated hazard products (Aqueduct/GFPLAIN/Global Flood DB/JRC v2.1) + local validation with SkySat/EMSN194 ([flood audit §10](flood-risk-scoring-methodology-audit.md#10-external-flood-hazard-products-as-the-proposed-path)) |
| 4 | **1 km → 250 m inheritance** on terrain/OSM metrics | Block-constant cells; false sub-km precision on map | Gate sub-km claims to HAND/FRI-sampled fields; refactor grid pipeline (§3, [data-risk-audit §3](data-risk-audit.md#3-per-layer-risk-register)) |
| 5 | **Unvalidated weight vector + POA masks** (`lakesideRisk`, `deltaRisk`, ad hoc weights) | Prioritization reflects POC tuning, not calibrated science | Internal screening only; ON-5680 calibration / config ([flood audit §5](flood-risk-scoring-methodology-audit.md#5-hardcoded-parameters)) |

## 2. Data inventory — what the POC renders

**Goal (ON-5679):** Every dataset and derived layer the POC renders in one register, with shared columns.

**Origin** must be exactly one of:

| Origin | Meaning |
|--------|--------|
| `OEF catalog S3` | Tiles on `geo-test-api.s3.us-east-1.amazonaws.com` from the geospatial-data pipeline; app uses `/api/geospatial/tiles/{tileLayerId}/…` and optionally `/api/geospatial/proxy-tile?url=…` |
| `POC local cache` | Static files under `client/public/` shipped with the app |
| `POC fetched at runtime` | Request-time fetch (Overpass, Copernicus DEM tiles, boundary API, etc.) |
| `POC computed inline` | Derived in browser or server from other inputs (`gridService`, spatial queries, zone generators) |

**Canonical code references:** `shared/geospatial-layers.ts`, `server/routes/tileProxyRoutes.ts`, `client/src/core/pages/site-explorer.tsx`, `client/src/core/contexts/sample-data-context.tsx`, `POST /api/geospatial/grid` + `server/services/gridService.ts`, offline scripts under `scripts/`.

## 5. Offline sample pipeline vs live `gridService` — diff and recommendation

_See `docs/site-explorer-data-audit.md` §7. This section records the **current divergence** between paths and the **target architecture** for hazard scoring and derived products._

### 5.1 Target architecture: compute offline, load in the platform

**Recommendation (ON-5679 / ON-5680):** All **methodologically complex** geospatial calculations—composite hazard scores (`flood_score`, `heat_score`, `landslide_score`), per-cell metric bundles used for scoring, intervention zones, and pre-rendered risk rasters—should be produced **offline** (data-team notebooks, `geospatial-data` ETL, and versioned scripts under `scripts/`) and **published as artifacts** (GeoJSON grid, value tiles on S3 or `client/public/`, catalog entries). The NBS platform should **load and visualize** those products; it should **not** recompute them in the browser or on the app server at request time.

| Layer | Offline (target) | In-app (acceptable scope) |
|-------|------------------|---------------------------|
| OEF catalog rasters (HAND, FRI, CHIRPS, ERA5, etc.) | Precomputed in CCRADiscovery / `geospatial-data`; tiles on S3 | Proxy/fetch tiles only (`/api/geospatial/tiles/…`) |
| Per-cell metrics + hazard scores | `generate-grid-250m.ts` → `recalc-scores-v3.ts` → `porto-alegre-grid-250m.json`; `generate-risk-tiles.ts` | **Do not** duplicate formulas in `gridService.ts` for production |
| Intervention / neighborhood zones | `generate-intervention-zones.ts`, `generate-neighborhood-zones.ts` → static JSON | Display + filter only |
| Light client logic | — | Map UX, legends, thresholds for **display** (e.g. spatial queries that **filter** precomputed value tiles at centroids—see §2.1 `sq_*` rows) |
| Live exploration (non-sample API) | Same offline artifacts per city/release | Boundary + OSM vector fetch OK; **not** a second scoring implementation |

**Why (audit view):**

1. **Reproducibility and testing** — Offline scripts are versioned, runnable in CI or batch jobs, and comparable run-to-run; inline API scoring drifts from `recalc-scores-v3.ts` (see table below) and is hard to regression-test.
2. **Documentation and peer review** — Methodology audits and product docs reference **one canonical scorer** per hazard; dual paths (`gridService.ts` vs scripts) create doc/code drift ([flood audit §6](flood-risk-scoring-methodology-audit.md#6-live-api-path-not-used-in-sample-mode)).
3. **Performance** — Sampling HAND, FRI, HWM, SoilGrids, and multi-source composites for tens of thousands of cells belongs in batch/ETL, not per `POST /api/geospatial/grid` request.
4. **Governance** — Data team owns release tags, catalog `dataset_id`, and S3 paths; the app consumes **released** layers rather than embedding evolving formulas in TypeScript.

**POC exception (acknowledged):** Computing scores inside `gridService.ts` or the client was a **fast path to demo** arbitrary cities without pre-building every grid. That is reasonable for a **prototype** (“show something quickly”), but it is **not** the architecture to extend for Porto Alegre production, methodology hardening (ON-5680), or city handoff. Sample mode already follows the target pattern: Site Explorer reads **`porto-alegre-grid-250m.json`** and local **`/tiles/*_risk/`** from offline pipelines—not live `api_grid` scores.

**Migration steps (recommended):**

1. Treat **`recalc-scores-v3.ts`** (and successors) plus **`generate-grid-250m.ts`** as the **only** writers of `flood_score` / `heat_score` / `landslide_score` for shipped cities.
2. **Deprecate** hazard composition in `server/services/gridService.ts` `computeCompositeScores` for production; if `POST /api/geospatial/grid` remains, return precomputed metrics from stored grid or return **inputs only** with a clear “scores not computed live” flag.
3. Publish scores as **catalog or POC static assets** (grid GeoJSON + `tiles_values/*`) after each methodology change; bump a `methodology_version` or build id in metadata.
4. Reserve in-app computation for **non-scoring** interactions (Overpass layers, spatial filters on existing value tiles, UI thresholds)—not for reimplementing FRI/HAND/UHI composites.

**Show-to-city gate:** Do not present live API hazard scores as equivalent to offline v3 unless a reconciliation test proves bit-for-bit or documented parity. Default narrative: **“scores from offline build (date / methodology version)”**.

### 5.2 Current divergence (offline vs live)

| Topic | Offline pipeline | Live `gridService` |
|-------|------------------|---------------------|
| Entrypoints | `generate-sample-grid.ts` → `generate-grid-250m.ts` → `recalc-scores-v3.ts` → `generate-risk-tiles.ts` / zone scripts | `POST /api/geospatial/grid` |
| Production path today (POA sample) | **Yes** — bundled JSON + local risk tiles | **No** for Site Explorer sample mode |
| Metrics count | ~20+ fields on `properties.metrics` (§2.2) | ~11; no HAND, FRI, HWM, SoilGrids, D8, `building_density` |
| Hydrological / hazard rasters | HAND, FRI, EMS depth, CHIRPS, Dynamic World sampled in `generate-grid-250m.ts` | Not sampled |
| Score formulas | v3 composites in `recalc-scores-v3.ts` | Simpler proxies in `computeCompositeScores` (e.g. flood = river + low-lying + impervious only) |
| Landslide | Slope, precip, soil, vegetation | Placeholders (`S=0`, `U=0`); effectively canopy-only |
| **Recommendation** | **Canonical** — extend and harden this path (§5.1) | **Do not extend** for methodology; converge or read-only |

## 6. Cross-checks vs frameworks

_Short comparison to: IPCC AR6 (hazard × exposure × vulnerability), ThinkHazard!, EEA NBS Atlas — where the POC aligns or diverges, and whether divergence is justified._

**Status:** Completed write-up for **[ON-5775](https://openearth.atlassian.net/browse/ON-5775)**. Flood-specific hazard vs risk terminology remains detailed in [flood audit §2.6](flood-risk-scoring-methodology-audit.md#26-terminology-flood-hazard-vs-ipcc-flood-risk).

### 6.1 Comparative read: what each framework/tool is for

| Element | Primary focus | How it operates | What data/information it covers | What it provides | Strengths | Limits for CCRA |
|---------|---------------|-----------------|----------------------------------|------------------|-----------|-----------------|
| **IPCC AR6 risk framing** | Conceptual framework for climate risk as an **interaction** between hazard, exposure, and vulnerability (not hazard-only). | Not a platform or database; a methodological structure for selecting indicators, assumptions, and causal links. | Hazard processes/trends, exposed people/assets/ecosystems, vulnerability (sensitivity + adaptive capacity), and changing conditions over time. | A defensible structure for risk indices, impact chains, sector studies, and decision narratives. | Strongest scientific framing for a robust CCRA and for avoiding hazard-only claims. | Does not prescribe one fixed operational formula, dataset, normalization method, or city-scale implementation path. |
| **ThinkHazard!** | Rapid multi-hazard **screening** for project planning and early disaster-risk checks. | Users query a location; tool returns hazard classes (e.g., low/medium/high) and general risk-management guidance. | Global hazard layers from mixed public/academic/government sources across flood, coastal flood, cyclone, drought, seismic, landslide, etc. | First-pass hazard signal and practical recommendations. | Fast, communicable, useful as an early warning/radar of relevant hazards. | Not a full CCRA risk engine: limited local exposure/vulnerability integration, coarse comparability for urban design, not a high-resolution local assessment. |
| **EEA / Urban Nature Atlas (NBS Atlas)** | Knowledge base of urban NBS interventions, typologies, governance, and implementation examples. | Searchable atlas/database by challenge, intervention type, geography, and project features. | Case-level NBS information: typologies, benefits/co-benefits, implementation context, governance, financing (where available). | Adaptation design options and precedent library. | Strong bridge from “identified risk” to “candidate NBS responses.” | Not a universal spatial risk-prioritization tool; mostly case/typology evidence rather than standardized local H-E-V metrics. |

### 6.2 How this maps to the current POC

| Question | IPCC AR6 | ThinkHazard! | EEA / Urban Nature Atlas | Current POC position |
|----------|----------|--------------|--------------------------|----------------------|
| Is it a framework, tool, or dataset? | Framework | Screening tool | NBS case/solution atlas | Mixed stack (tiles + offline composites + app logic) |
| Does it calculate climate risk directly? | Defines how to structure it | No (hazard screening) | No (solution library) | **Partially**: current layers are mainly hazard/susceptibility; full H-E-V risk is not computed end-to-end |
| Does it include hazard? | Yes (conceptually) | Yes (core output) | Indirectly (challenge context) | Yes (`flood_score`, `heat_score`, `landslide_score`, FRI/HWM/etc.) |
| Does it include exposure? | Yes (conceptually) | Limited | Indirect/case context | Partial: exposure layers exist (WorldPop/OSM/GHSL), but are not integrated consistently as formal risk components |
| Does it include vulnerability? | Yes (conceptually) | Not deeply for CCRA | Sometimes qualitative/contextual | Mostly missing as a formal, explicit vulnerability component in current scoring formulas |
| Is it suitable for local spatial prioritization? | Yes, if operationalized | Initial signal only | Partial (for solution ideation) | Useful for screening/prioritization workshops; not yet decision-grade municipal risk assessment |
| Is it suitable for NBS design? | Helps justify why/where to act | Helps identify relevant hazards | Strong for intervention typologies and precedents | Strongest when used after hazard hotspots are identified |

### 6.3 Alignment/divergence judgment (and whether divergence is justified)

| Framework/tool | Alignment with POC | Main divergence | Is divergence justified in this POC stage? | Show-to-city gate |
|----------------|--------------------|-----------------|--------------------------------------------|-------------------|
| **IPCC AR6** | POC already distinguishes hazard signals and acknowledges limits in flood audit terminology ([flood §2.6](flood-risk-scoring-methodology-audit.md#26-terminology-flood-hazard-vs-ipcc-flood-risk)). | Current scores are mostly hazard/susceptibility; exposure and vulnerability are not fully integrated as a formal H-E-V risk product. | **Partially** (acceptable for prototype screening, not for official risk claims). | Label outputs as **hazard screening / susceptibility**, not complete IPCC-style risk. |
| **ThinkHazard!** | POC has similar first-pass hazard-screening behavior via FRI/HWM and map overlays. | POC is city-pipeline specific and has score construction choices (weights, constants) beyond ThinkHazard!'s simple class output. | **Yes** for early prioritization context; **no** as a substitute for local CCRA risk quantification. | Use as external sanity check / hazard radar; do not treat as final risk evidence. |
| **EEA / Urban Nature Atlas** | POC objective (NBS project preparation) aligns with using an atlas for intervention options and precedent. | Atlas content is not a local quantitative risk layer and cannot replace spatial hazard/exposure/vulnerability analysis. | **Yes** for adaptation design phase after risk hotspots are identified. | Use for solution pathways and examples, not for proving local risk magnitude. |

### 6.4 Recommended combined workflow (framework-consistent)

1. **IPCC AR6 framing:** use H-E-V as the methodological backbone and disclosure structure.
2. **ThinkHazard! (or equivalent global screening):** use as initial hazard triage/sanity check.
3. **Local geospatial data + city-specific methods:** produce the operational hazard/exposure/vulnerability assessment for the city context.
4. **EEA NBS Atlas (and related NBS catalogs):** translate identified risk hotspots into plausible intervention portfolios.

**Audit implication:** This sequencing is the most defensible way to explain current outputs and roadmap work under ON-5680: keep present layers framed as screening-grade hazard products, then strengthen toward explicit H-E-V integration and city-specific validation before decision-grade claims.
